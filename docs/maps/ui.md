([design README](../design/README.md), Engineering). Crates are

**Keep this current.** Add, move or remove a screen part, picker or slash command →
update this page in the same commit.

## The screen, top to bottom

Full-screen is the default (M1c, `mode/mod.rs`). The app runs on the alternate screen and `Tui` draws the frame. Rows top to bottom (`docs/design/tui.md`):

```
start header ─ start screen: ` hoocode v<ver>` bold, ` <cwd> · N skills · M agents` dim; once a turn is in the transcript: one blank row (top chrome)
  attach slot ─ the attached subagent's header, when attached (top chrome)
┌ body ─ transcript (chat). Live: follows the tail. Pinned: holds still ─┐
└────────────────────────────────────────────────────────────────────────┘
  pending messages, status, widgets above
  task panel ─ TodoWrite plan items, subagent runs
  notification rows ─ tips and notices longer than one row (plain dim rows, max 3 for a message; a yellow title for a warning)
  completion menu ─ slash, @file and argument choices, above the prompt
  transient rows ─ runtime warning, retry notice, extension statuses, startup progress
  prompt ─ ` ›` on the surface colour, no frame, grows with input; queued messages are dim ` ○ text · sends after …` rows above it; dialogs replace it
  status line ─ left: working timer, a one-row notice, not signed in, last turn result, or (pinned) scroll / search; right: session · model · context · cost
```

`HOOCODE_FULLSCREEN=0` turns full-screen off for one run (the env var wins over the `fullscreen` setting, default `true`; `fullscreen_enabled` in `mode/mod.rs`). Off, the screen is the inline tree: the same rows, with a flex spacer (`screen_fill`) after the start header and the chat in place of the body. The status line is the last row in both modes; there is no HUD and no footer.

The inline tree (off) from top to bottom: the start header, a flex spacer (`screen_fill`), the attach slot, the chat, then the rest as above. When a buffer taller than the screen shrinks (a picker, the autocomplete or a tall prompt folds), the window is held: the rows below the prompt go blank until content grows back into them, and no row is drawn again into the terminal's scrollback. A change to a row already in the scrollback (a panel pushed up by a tall prompt, then changed) is a full redraw with the scrollback cleared, so no stale copy stays; `terminal.clearOnShrink` makes every shrink a clean redraw (`paint_live` in `hoocode-tui-render/src/tui.rs`, `tests/it/scrollback_fold.rs`). The full-screen tree (on): the start header, the attach slot (top chrome), the body (chat), then the rest as above. Root children before the body are the top chrome, those after it the bottom (`Tui::set_fullscreen_body`). While pinned, the scroll status replaces the bottom's last row, the status line (`Tui::set_scroll_status_in_bottom`), unless a focused picker took the bottom.

Exit leaves the alternate screen and prints nothing (`Tui::stop`). SIGTERM and SIGHUP restore the terminal first, then exit 128 plus the signal (`tui-terminal/src/interrupt.rs`, `install_terminate_restore`, M1e). A UI-thread panic restores it too (the panic hook).

## Pickers and dialogs

They replace the prompt frame while open. All in `code-tui-selectors/src/` unless noted.

Every picker, card and the task panel draws on a **pane** (`code-tui-widgets/src/pane.rs`, declutter spec v2.4/v2.9). In colour a pane is borderless on its own background: a title row (` Title ` chip, accent or yellow `Chip::Warn` for blocking cards, then the dim `/command` and facts), the rows behind a 3-column gutter (` › ` on the selected row only, blank elsewhere), an optional input row at the bottom (input background, typed text with a trailing `▏` caret, or `▏` plus the dim placeholder when empty) and the hint row last (`hint_line` / `capped_hint_line` / `fit_hint_line`: at most 4 items + `f1 more`, `enter` and `esc` never drop, yellow only for blocking). Overlong title, hint and input rows flow onto continuation rows (`flow_text`) instead of truncating. A pane with `detail` rows splits list | detail at ≥100 columns (blank 1-column gutter, detail one stronger shade); narrower, the detail stacks under the list capped at 3 rows (`STACKED_DETAIL_ROWS`), then `…` (or hides, `NarrowDetail::Hidden`). With colour off (NO_COLOR, `TERM=dumb`) it gets light `┌─┐│└┘` borders with the title in the top border, ` › ` + bold on the pick, a `│` between list and detail, and no rule above the input row. Colours come from `PaneStyle::current`: the theme tokens `surface`, `pane`, `paneSel`, `paneInput`, `paneDetail`, `chip`, `chipWarn`, `chipFg`, plus `ink`/`dim`/`acc`. Pickers map onto it through `Console` (`console.rs`: the name `Models · /model` becomes the chip `Models` and the command `/model`; `detail`, `list_width`, `row_width` pass through to the pane; `help_rows` lists the full key list after `f1`; the query becomes the input row), cards through `render_card` (`card_frame.rs`: warn chip, right label as facts, foot as hint row). Goldens `pane_*`. A click selects a row; `enter` opens it (no second-click pick).

Every picker moves its cursor with `PickerCursor` (`tui-components/src/picker_cursor.rs`): up and down, PgUp and PgDn by a window, Home and End to the ends. The ends clamp; nothing wraps (decision 29). The visible window and the `(n/len)` footer come from the same type. The `hoocode config` list skips its group headers and counts resources in its footer. In a picker with a query line (`/model`, scoped models, `/login`, `/resume`, `hoocode config`), Home and End stay with the query's text cursor, and only PgUp and PgDn jump the list (`handle_query_key`). ## Scroll-back (pinned view)

Live: the view follows the newest output. Pinned: the view holds its row while output arrives.
The TUI owns the mechanism; the app owns which key does what.

**Behaviour**

- Scrollbar: last column, only while pinned and the transcript is taller than the view.
- The transcript renders one column narrower while the bar shows.
- `┃` is the thumb, `░` the track. The shapes differ, not only the colour.
- Click above the thumb: page up. Click below: page down. On the thumb: nothing.
- A picker or ask-options pane with focus paints its lines at the bottom, above the status row.
  The transcript keeps at least one row.
- Pinning works from any focus. Picker keys never un-pin.
- PgDn past the bottom, or the wheel reaching the bottom, returns to live.
- Status row (bottom): the REWIND bar while pinned (`◂◂ REWIND  43–61 of 78 · 55%  ↓ 3 new`, label in vio, then the keys: line, `PgUp/PgDn page`, top, live). The SCAN bar while searching (`⌕ SCAN  query  N contact(s)`, label in warn; typing: `enter lock · esc close`; locked: `enter next · esc close`).
  The line keys are `↑/↓` and `j` / `k` over an empty prompt, and `shift+↑/shift+↓` while the prompt holds text.
- Full-screen and mouse reporting on (the default): a plain drag does not select text. Selection is shift+drag.
- The view pinned on a message keeps that message on top across renders.
  A rebuild of the transcript (`/new`, `/resume`, the thinking toggle, leader `b`) goes live.
- Full-screen (M1d, the default): the body is the transcript (header and chat). The bar row sits above the bottom,
  and carries `↓ N new` while pinned: lines that arrived since the view last pinned or moved. A shorter transcript
  (a clear) starts the count again. The scrollbar column is always reserved (blank while live, so pinning does not
  reflow), and its glyphs are drawn per body row while pinned. Search marks its matches in the body (`◂ contact` on each matched row) and steps with enter/`n`/`p`. A focused
  picker replaces the bottom rows while pinned. A body image whose picture would reach above the body is named
  `[image]`.

## Task panel

One tab per kind of task: **Plan** (TodoWrite items, each linked run nested under its item), **Agents** (the subagent forest; background runs too, each a row like a Shell job), **Schedule** (scheduled jobs, one row each, with `next in …`), **Shell** (background shell jobs, one row each: running with Abort, then done, failed with its exit status, or killed; the rows are `shell:<id>`, published by `hoocode-code-tool-bash` `jobs.rs`), **MCP** (MCP servers and calls). A tab shows only while it has rows. The panel is a pane (`render_flight_plan`): unfocused it has no title, and a dim strip row comes first only when more than one tab has rows (`tab_strip`: `plan 2/5 · agents 1 running · ctrl+x g`, the shown tab in normal text, the others dim; the pane cuts it with `…` when narrow); focused it has the `Tasks` chip, `/tasks · ctrl+x g` and the strip as the title facts, and the hint row. A tab's `N running` counts the running rows only. The plan's `done/total` covers every item the last TodoWrite sent: `TaskStore::reset` (each new user message) keeps the whole plan while any item is open, done ones included, and drops it whole once all are finished, or once `PLAN_IDLE_MESSAGES` (3) user messages pass with no TodoWrite (`TaskStore::note_plan_write`, called by `reconcile`), so a plan the agent never closed does not stay forever. It draws the same at every density. The rows show at most 6 (`PANEL_MAX_ROWS`), or a quarter of the terminal's height on a short one (`row_cap`, height set per pass by `set_screen_rows`), windowed around the pick; the rows left out show as a `N more` row under them. The plan is rebuilt from the session's last successful TodoWrite on resume, reload and tree navigation (`restore_plan` in `hoocode-code-tools-optin`, called from `render_initial_messages`). Adding a kind means a `TaskPanelView` variant, its label, and a rule in `lens_rows`.

**Shown or hidden.** Shown by default. The leader's `g` (`app.panel.focus`, ctrl+x g) toggles it. The toggle is per session (`is_shown`, `toggle_shown`). With no rows the leader `g` does not flip the toggle: the status line says `No tasks to show.` With no rows the panel draws nothing either way. The `›` pick marker and the hint foot show only while the keyboard is in the panel.

**Keyboard.** The prompt keeps the keyboard. Up on the prompt's first visual line (no autocomplete list open) hands it to the panel on its bottom row, but only while the panel can take it: shown, with rows, and the transcript not pinned. `CustomEditor` reads that from the shared `panel_takes_up` flag, which the app refreshes before each key (`refresh_panel_takes_up`); otherwise Up goes to the editor as a cursor move. The hand-off runs straight after that key (`hand_off_panel_up`), so the keys after it in the same input batch reach the panel. A panel that gives the keyboard back (Down past the last row, Esc) does so at once too (`return_panel_focus_if_asked`). A panel with the keyboard that loses its rows, or is hidden, gives it back before the next key (`release_stale_panel_focus`, also on each pass). Left and Right land the pick on the new tab's last row, so Down returns from there. Shift+Up and Shift+Down are the prompt's history (`tui.editor.historyPrevious` / `historyNext`); the plain arrows only move the cursor.

|---|---|
| Tabs, rows, pick, tab strip, hint foot, cancel arming, shown/hidden, the tick (`ticking`, while any row in any tab is running) | `code-tui-widgets/src/task_panel.rs` (`TaskPanelComponent`, `RowModel`, `PanelEvent`, `render_flight_plan`) |
| Leader `g` (ctrl+x g), the Up hand-off, what the app does with events (`Open`, `Cancel`, `Exit`), the pool cancel | `hoocode-code-tui-app/src/mode/task_panel.rs`; `Action::PanelToggle` / `PanelUp` in `mode/input.rs`; events drained in `mode/mod.rs` `run` |
| Keys (`app.panel.*`) | `hoocode-code-tui-keybindings/src/keybindings.rs`; listed on `/hotkeys` (`code-tui-widgets/src/controls.rs`) |

**Keys.** Once the panel has the keyboard (`Tui::set_focus`), its keys are:

| Key | Focused panel |
|---|---|
| `app.panel.focus` | Not a panel key: the leader `g` (ctrl+x g) runs it from the prompt. Esc returns the keyboard |
| `app.panel.up` / `app.panel.down` (arrows) | Pick the row above / below. Up clamps at the top; Down past the last row returns to the prompt. The pick is kept by row id across rebuilds |
| `app.panel.prevTab` (Left, Shift+Tab) / `app.panel.nextTab` (Right, Tab) | Previous / next tab with rows (wraps); the pick goes to the new tab's last row |
| `app.panel.open` (Enter) | A row with an action (MCP server `Login`) queues `Perform`, which `TaskStore::perform` runs (`/mcp login` path). A subagent row queues `Open`, which attaches to its run (`attach_run`, T3.3). A shell row queues `Open`, which attaches to the job's output (`attach_job`, T5.3). Plan items, schedule jobs and MCP calls do nothing on Enter |
| `app.panel.cancel` (`x`) | First press arms the row (the right column says `press x again to cancel`). Second: an Abort row (MCP call, running shell job) queues `Perform(Abort)`; a running subagent run queues `Cancel`, through `SubagentPool::cancel`. Other rows ignore it. Any other key disarms |
| `app.panel.exit` (Esc) | Disarms a pending cancel, else back to the prompt |

The hint foot names only the keys that do something on the picked row (`pick_hints`): the moves and `esc back` always, then Enter and `x` by row kind (`enter log in` on a Login row, `enter open its log` on a run, `enter open output` on a shell job, `x cancel` on an active run or MCP call, `x stop` on a running shell job). A plan item or a schedule job names neither.

**Not yet covered by a test:** the pinned view keeping Up (`refresh_panel_takes_up` checks `scroll_pinned`), and the hand-off and the stale-focus release through the whole app (the prompt's flag decision is unit-tested in `mode/input.rs`, the panel's parts in `code-tui-widgets` tests, and the release rule in `mode/task_panel.rs`).

## Attached view (subagent transcript or shell output)

Attach shows one subagent run's transcript, or one shell job's output (T5.3), on the chat area, read-only, with the header row above it and the prompt's place taken by a hint. Esc goes back, and the session's transcript and scroll come back as they were. Ctrl+C and Ctrl+D go back too (the view takes the keyboard). A session switch (`/new`, `/resume`, `/fork`, `/import`, `/cd`) detaches first (`take_session_runtime`).

**Shell output (T5.3).** Enter on a Shell row shows the job's log (`<session>/jobs/<id>.log`): the last 32 KiB at first, as plain text (escape sequences and carriage returns dropped), then followed once a second on the tools pool while the job runs. Once the job has ended, its output is closed (no process of its group is alive, so a background child that still writes keeps it open: `jobs.rs` `output_open`) and its log is read to the end, the view stops polling. The header reads `› shell · <command> · running | done | exit N | killed · esc back`; the hint says it is a shell job's output. A read that started from an earlier position is dropped, so no text shows twice. Each tick's read (`jobs.rs` `follow_log`) catches up to the end of the log in bounded chunks (up to 256 KiB a tick); a follower more than 64 KiB behind skips to the tail, and the view marks the gap (`… output skipped`). Files: `mode/job_tail.rs` (`JobTail`, the view's text and `accepts`, `state_word`), `mode/attach.rs` (`attach_job`, `poll_shell_tail`, `shell_tail_read`), `hoocode-code-tool-bash` `jobs.rs` (`follow_log`, `read_log`). Off the UI thread: the read runs on the tools pool and returns as `AppEvent::ShellTail`; if the pool cannot run it, the view gets the error and stops following instead of freezing.

**Where the output goes.** A job's stdout and stderr are the log file itself (no pipe), so the job keeps writing after hoocode exits (Leave running). The log is created new (`create_new`), so a job never appends to an older job's log of the same number.

## Quit with shell jobs running (T5.3)

A quit (Ctrl+D, Ctrl+C twice, `/quit`, or a fatal session error) with shell jobs running asks once: "N background shell job(s) still running. Quit?" with **Kill all** (the default) and **Leave running**. Kill all signals each job's process group (`jobs::kill_all_jobs`) before the app exits. Esc keeps the app open, and the next quit asks again. A quit asked again while the prompt is up does nothing. Files: `mode/task_panel.rs` (`QuitJobs`, `ready_to_quit`, `quit_jobs_answered`); the event loop in `mode/mod.rs` `run` asks `ready_to_quit` where it used to break on `exit_requested`. After the loop, `mode/mod.rs` `run` calls `mode/shutdown.rs` (abort the agent, kill the tool process groups, flush the session, close MCP, release, then restore the terminal; each step has a deadline, concurrency.md §4).

|---|---|
| Header row and hint (pure components, goldens) | `code-tui-widgets/src/attach_view.rs` (`AttachHeader`, `AttachPrompt`) |
| Attach, detach, the run's history (read on the tools pool), the run's live events, `/agents` rows | `hoocode-code-tui-app/src/mode/attach.rs` |

| Screen check | `scripts/tui/scenarios/subagent-attach.json` (tmux, the mock LLM; the attach, live and finished, and the way back) |

**How it works.** The chat container is shared by the session and the attached run. Two halves exist, and `Attached::main_in` says which one is on screen; `flip_view` swaps them. The session is on screen by default. The run's half is shown only in three windows: the run's own events (`apply_attached_event`), a key to the screen (`accept_terminal_event`), and the render at the end of the loop. A session handler therefore runs against the transcript it always wrote, and the run's view is never changed by it. While attached, a session event does not set the dirty flag (its change is drawn on the next one-second tick).

## Rules for UI changes

- Screen goldens: about 10 key interactive screens, a pre-release check. `python3 scripts/tui/goldens.py check all`
  runs the real binary in tmux against the mock LLM (`scripts/tui/mockllm.py`) and diffs each screen with
  `tests/golden/tui/<scenario>/`. Scenarios are in `scripts/tui/scenarios/`. A deliberate
  change is accepted with `goldens.py update <scenario>` and shows in the diff. Component goldens
  (`tests/golden/<crate>/`) run in nextest; accept them with `UPDATE_GOLDENS=1`. The screens
  are hoocode's own.
- Concurrency ([runtime.md](../design/runtime.md)): the UI thread never does
  file or network I/O. Work off the UI thread reports back through `AppEvent`.
- Attached view: code that writes to the transcript (`self.transcript`, `add_to_chat`) runs
  with the session on screen, which is the loop's default. Only the attached run's events and
  the render go through `show_attached`; a new window needs the same care.
