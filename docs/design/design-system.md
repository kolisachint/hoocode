# Design system: where the TUI styling stands and where to take it

Status: proposal, 2026-10-16. Design only; no code changes. Needs steer on the four
open questions before any build card starts.

## Goal

One source of truth for how hoocode looks, so that a theme change, a new glyph or a new
component touches one place. Keep the screen readable for low vision and colour blindness
(the `colorsafe` themes). Keep the token count small enough that a new theme is a short file.

## Decisions (recommended, pending steer)

1. **Fix the authoring surface before adding features.** Theme files are the source. Shrink the
   palette from 57 foreground and 12 background tokens to a semantic core of about 20, and derive
   the markdown, syntax and thinking tokens from it. (Option A below.)
2. **Ship three themes by default:** `dark`, `light`, and the `colorsafe` pair. Move `solarized-*`
   and `vox-cutout-*` to an optional theme pack. (Option B.)
3. **One glyph module.** Glyph literals repeat across crates. Put them in one module and import it.
4. **Repair the stale schema reference.** Every theme file points `$schema` at the retired
   `hoocode-ts` repository. Point it at the schema in this repo.
5. **Generate the design-system export from the theme files.** The Hoocode design system artifact
   (published 2026-10-16) was extracted by hand. It should be a generated view of the theme files,
   not a second copy that drifts.

## What we build

Each step is small and keeps the screen goldens unchanged, or says why it changes them.

| Step | What | Size | Gate |
|---|---|---|---|
| D1 | Point `$schema` at the in-repo schema in all 8 theme files. Check the schema test still passes. | S | `hoocode-code-tui-theme` tests |
| D2 | `glyphs` module: move `✓ ✗ ⊘ ├ └ │ ▰ ▱ ·` and the `brand.rs` glyphs into one place. No output change. | S | component goldens identical |
| D3 | Token audit: list every token and the code path that reads it (literal names, and names built in closures and maps). Report, do not delete. | S | audit doc |
| D4 | Semantic core: map the 57 tokens onto about 20 roles. Derive the markdown, syntax and thinking tokens from those roles. Keep the old names as aliases for one release. | M | contrast tests on all shipped themes; component goldens |
| D5 | Move `solarized-*` and `vox-cutout-*` to a theme pack. Keep the retired-name table working. | S | `/settings` theme list; theme tests |
| D6 | `theme → tokens.json` export script. Regenerate the design-system artifact from it. | M | the script output matches the artifact |

Work follows `docs/design/tui-activity.md`: Phase S (simplification) comes before feature
phases, and the TUI work is done by Haiku subagents under the main session's brief and review.

## Not doing

- A new theming engine, a CSS-in-terminal layer, or per-component theme overrides.
- Redesigning the screen layout. The layout in `docs/maps/ui.md` is the baseline.
- Icon fonts or images. The glyph vocabulary stays text.
- Removing `colorsafe`, `dark` or `light`.

## Open questions

1. **Token scope (decides D4).** Recommended: **A**, a semantic core of about 20 with
   aliases kept for one release. Alternatives: **B** keep all 57 and only document them (cheapest,
   keeps the authoring burden); **C** rewrite the theme format from scratch (largest, breaks
   user themes in the agent dir's `themes/` folder). Trade-off of A: user themes that set `mdCode` etc. keep
   working through aliases, but their values stop being independent.
2. **Shipped themes (decides D5).** Recommended: **keep** `dark`, `light`, `colorsafe-*`; move the
   rest to a pack. Alternatives: keep all eight (no churn, the test list stays long); drop `vox`
   entirely (fewest files, loses a tested theme).
3. **Where the design-system artifact lives (decides D6).** Recommended: **generated from the theme
   files**, committed under `docs/design/`, regenerated by a script. Alternative: keep the
   hand-maintained artifact as the brand book and accept drift.
4. **Compact chrome (not a theme question, found in review).** `docs/maps/ui.md` says compact keeps
   both footer rows. `crates/hoocode-code-tui-app/src/chrome_layout.rs` switches compact to a
   one-line footer and a summary task panel. Which one is intended? Recommended: the code is the
   likelier truth; fix the map.

## Details

### What the review found

Method: read the theme crate, all eight theme files, the registry and API, and grepped the
styling crates (`widgets`, `app`, `tui-components`, `cli`) for colour escapes, token use and glyph
literals. Counts are from the repo at branch `claude/design-system-extraction-6t4r9r`.

| Finding | Evidence | Read |
|---|---|---|
| The theme API is sound and the bypass is small. | 57 raw escape-sequence matches in the UI crates; almost all are input-protocol parsing (`\x1b[A`, paste markers) and test fixtures. Cursor uses inverse video (`\x1b[7m`), an attribute, not a colour. | Good. Keep the rule: colour goes through `Theme`. |
| The token set is large for the number of roles. | 57 foreground and 12 background tokens. Markdown, syntax and thinking alone account for 26 of the 57 names. | Consolidate (D4). |
| Literal token names undercount use. | A literal search finds 27 names passed to `fg`/`bg`/`fill`. The markdown renderer reads its tokens through closures (`tui.rs:298-304`), so the audit (D3) must read both. | Do not delete on a literal grep. |
| Theme files point at a retired repo. | `$schema` in `dark.json`, `light.json`, `colorsafe-*.json`, `vox-cutout-*.json`: `kolisachint/hoocode-ts`. `theme-schema.json` says "Pi coding agent". | Fix (D1). |
| Glyphs repeat across crates. | `✓` in 12 files, `✗` in 8, `├` and `└` in 6 each, `│` in 9, `·` in 28, `▰`/`▱` in 2 each. `brand.rs` holds only a few of them. | Centralise (D2). `tui-activity.md` L5 skipped this as too cross-crate; now recommended. |
| Contrast is tested, on a fixed list. | `theme_contrast.rs` checks 4 light and 4 dark themes against fixed token groups and minimums (7.0 for meaning groups, 4.5 for text). A new theme must be added to the list by hand. | Keep. Derive the list from the theme directory (part of D4). |
| Retired names are kept as aliases. | `RETIRED_THEMES` maps `high-contrast-*`, `warm-*`, `vox-*` to successors. | Good. Keep through D5. |
| The design-system artifact is a copy. | Hand-extracted from the theme files on 2026-10-16. Values match the source, and no tool regenerates them. | Generate (D6). |

### Two parallel "component" layers

Interactive lists live in `hoocode-tui-components` (`select_list`, `settings_list`, `picker_cursor`)
and in `hoocode-code-tui-widgets` (`selected_row_list`, `task_panel`). They share the cursor and
row logic in different forms. Not counted here: whether they can merge without a golden change.
That needs a read of each file, so it is a D3-style audit item, not a decision.

### Accessibility

- `colorsafe` pairs avoid red/green. The contrast tests run them in their own group (`ACCESSIBLE_THEMES`).
- Check, not yet verified: whether the `fill` chips still emit colour with the chalk switch off (the
  open point in `tui-activity.md` X15). If they do, `NO_COLOR` is not fully honoured. Verify before D4.
