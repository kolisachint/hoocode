# Contributing to hoocode

Thanks for helping. Bug reports, ideas, doc fixes and pull requests are all welcome,
and you don't need permission before opening a PR.

If you only want to report a bug or suggest something, you can stop here and
[open an issue](https://github.com/kolisachint/hoocode/issues/new/choose). The
templates ask for what a maintainer needs and nothing more. Security problems go
through [SECURITY.md](SECURITY.md), not a public issue.

## Reporting a bug

The three things that decide how fast a bug gets fixed:

1. **What you did**, precisely enough to repeat it.
2. **What happened**, and what you expected instead.
3. **`hoocode --version`**, your OS and terminal, and how you installed hoocode.

A report without exact steps is still worth filing. Say what you saw and how often.

## Suggesting a feature

Describe the problem before the solution. Sometimes the answer is a setting that
already exists, and sometimes the problem points at something better than the feature
you had in mind. The plan for what gets built next is in
[`docs/design/README.md`](docs/design/README.md); new features are designed there
first, as a short card, before any code is written.

## Setting up

You need [rustup](https://rustup.rs) and git. On macOS or Linux:

```bash
git clone https://github.com/kolisachint/hoocode
cd hoocode
cargo build                              # rustup installs the pinned toolchain on first use
cargo install --locked cargo-nextest     # the test runner CI uses
cargo run -p hoocode-code-main --bin hoocode -- --help
```

- **Toolchain.** [`rust-toolchain.toml`](rust-toolchain.toml) pins the toolchain
  (with rustfmt and clippy) so formatting and lints match CI. The minimum supported
  Rust version is **1.88** (`rust-version` in [`Cargo.toml`](Cargo.toml)); don't use
  newer language or library features.
- **Disk.** A full dev build is a few GB. Dev builds have `debug = false` to keep it
  that way. `scripts/dev/prune_target.sh` (dry run by default, `--apply` to delete)
  clears build output you haven't used for a few days.
- **Running your build.** `cargo run -p hoocode-code-main --bin hoocode` runs it in
  place. `scripts/install.sh` installs a release build as `hoocode` on your `PATH`.

## Finding your way around

The repo is a Cargo workspace of focused crates, named `hoocode-<area>-<what>`:
`ai-*` (providers, models, streaming), `agent-*` (the agent loop, sessions,
compaction), `code-*` (the CLI, tools, TUI app, settings) and `tui-*` (the terminal
UI library). The binary is in `crates/hoocode-code-main`.

Two maps tell you where things live. Read them before searching:

- [`docs/maps/packages.md`](docs/maps/packages.md): every crate and what it owns
  (generated by `scripts/maps/packages.py`)
- [`docs/maps/ui.md`](docs/maps/ui.md): every part of the screen, each picker and
  slash command, and the file that draws it

## The dev loop

After an edit, check just the crate you touched; it is much faster than a build:

```bash
cargo check -p <crate> --message-format=short
```

Build only when you need to run tests.

### Before you push

A change is done when these three pass:

```bash
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo nextest run -p <each crate you touched>
```

For clippy, `cargo clippy --fix --allow-dirty -p <crate>` fixes the easy ones; fix the
rest by hand. `cargo test -p <crate>` works too if you don't have nextest.

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs the whole workspace on
every PR: fmt, clippy, nextest on Linux and macOS, `cargo doc`, the test-layout check,
the dependency firewall and the repo guards. So a crate you didn't touch can still go
red; if it does and you think it isn't your change, say so in the PR.

### Tests

- **Unit tests** sit next to the code, in `#[cfg(test)]` modules.
- **Integration tests** go in `crates/<crate>/tests/it/<name>.rs` and are registered
  as a module in `crates/<crate>/tests/it/main.rs`, so each crate builds one test
  binary. CI fails on a test file anywhere else under `tests/`.
- **Component goldens** (rendered TUI components compared with checked-in text) run
  as normal tests. After a deliberate visual change, accept the new output with
  `UPDATE_GOLDENS=1 cargo nextest run -p <crate> <test>` and commit the updated files
  under [`tests/golden/`](tests/golden).
- **Screen goldens** run the real binary in tmux against a scripted mock model, for
  about ten key screens. They are a pre-release check, not needed for every PR. They
  need tmux and a built binary:

  ```bash
  cargo build -p hoocode-code-main --bin hoocode
  python3 scripts/tui/goldens.py check all          # reports in target/tui-goldens/
  python3 scripts/tui/goldens.py update <scenario>  # accept a deliberate screen change
  ```

- **Subagent evals** (`scripts/eval/subagent_evals.py`) and **fuzzing**
  ([`fuzz/README.md`](fuzz/README.md)) run nightly in CI. You only need them when you
  work on subagents or on a parser.

If you fix a bug, add a test that fails without the fix.

### Code style

- Match the file you're editing. Comments explain why, not what.
- Prefer owned types, `Arc` and `.clone()` over lifetimes in structs. Use plain
  `async fn` (also in traits); avoid hand-written futures and long combinator chains.
- Errors use hand-written error enums like the ones already in the crate. Don't add
  `anyhow` or `thiserror`.
- New dependency: check the version that resolved in `Cargo.lock` and read that
  version's API (`cargo doc`, or its source). Run
  `python3 scripts/ci/check_dep_firewall.py`; it enforces which crates may depend on
  what.
- Everything is named `hoocode`: crates `hoocode-*`, data in `~/.hoocode`, environment
  variables `HOOCODE_*`. `scripts/ci/no_cortex.sh` checks that the project's old name
  doesn't come back.

### Keep the maps current

If you add, rename or remove a crate, run `python3 scripts/maps/packages.py` and commit
the regenerated `docs/maps/packages.md` (CI runs it with `--check`). If you add, move
or remove a part of the screen, a picker or a slash command, update
`docs/maps/ui.md` in the same commit.

### Changelog

User-visible changes get a short entry under `## [Unreleased]` in
[`CHANGELOG.md`](CHANGELOG.md): a heading that says what changed and the date, then a
few bullets written for users. Refactors and test-only changes don't need one. Don't
bump versions; the release workflow does that.

## Licence and copied code

hoocode is MIT-licensed, and by contributing you agree your work is released under
the [MIT licence](LICENSE).

**Only copy code from MIT-licensed sources.** Don't paste code, schemas or generated
types from projects under other licences (Apache-2.0 included) into this repo.
Depending on a permissively licensed crate is fine, and so is running another tool in
a test.

## Opening a pull request

- **One change per PR.** Two unrelated fixes in one diff take more than twice as long
  to review.
- **Say why.** The diff shows what changed; the description should say what problem
  it solves and how you checked it.
- **Big changes: open an issue first.** A new provider, a change to the agent loop or
  a new top-level command is worth a quick discussion before you spend a weekend on it.
- **Using a coding agent is fine** (this is one). The repo's agent instructions are in
  [`CLAUDE.md`](CLAUDE.md). You should still be able to explain every line of your PR.

## Releases

Maintainers release by merging a PR labelled `rust:patch`, `rust:minor` or
`rust:major`. [`merge-release.yml`](.github/workflows/merge-release.yml) then runs
[`release.yml`](.github/workflows/release.yml): it bumps the workspace version, tags
`vX.Y.Z`, creates the GitHub release, and [`binaries.yml`](.github/workflows/binaries.yml)
builds the four platform archives, `SHA256SUMS`, and the npm and PyPI packages.
Add the label `release:run-gates` to re-run CI before tagging.
The release ships the merged PR: `release.yml` fails, and releases nothing, if `main`
has moved past the PR's merge commit. Dispatch `Release` by hand to ship the current
`main`. npm and PyPI publish only after `SHA256SUMS` is on the release. Releases share
one concurrency group; GitHub keeps one waiting run, so a run shown as cancelled
while queued did not release and needs dispatching again.

A release can also start from a tag. Bump the version on `main` first
(`python3 scripts/bump_versions.py <patch|minor|major>`, then `cargo update --workspace`
so `Cargo.lock` matches), commit, and push a tag that matches it
(`git tag v0.2.0 && git push origin v0.2.0`).
[`release-tag.yml`](.github/workflows/release-tag.yml) checks the tag against the
workspace version, runs the CI gates, creates the GitHub release and builds the same
artifacts. It stands down if a release for the tag already exists or the commit is the
`Release vX` commit made by `release.yml`, so nothing is published twice.

To rehearse, run `Release from tag` by hand (Actions → Run workflow, on `main`) with
the tag you plan to push and `dry_run` left on. It runs the checks, the gates and the
four builds (kept as artifacts) and publishes nothing. All crates share one version, set in the workspace `Cargo.toml`.

Before a release, re-record the README demo so it shows the current screens:
`scripts/demo/record.sh` builds a release binary, runs it in tmux against the scripted
mock model ([`scripts/demo/demo.json`](scripts/demo/demo.json)), and writes
`docs/assets/demo.gif`. It needs tmux, ffmpeg, node with Playwright and a Chromium
(see [`scripts/demo/record.py`](scripts/demo/record.py)). Look at the GIF before you
commit it.
